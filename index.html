Ocean Intelligence

A full-stack vessel research application that turns historical AIS observations and public registry records into an explorable research workflow.

View the source on GitHub ↗

The problem

Maritime data is incomplete, sometimes conflicting, rate-limited, and easy to overstate. The application needs to make useful evidence understandable without presenting historical observations as live or verified truth.

What I built

A React and TypeScript interface backed by an ASP.NET Core API. The backend owns authenticated Global Fishing Watch requests, validation, caching, concurrency control, rate limiting, and safe error mapping. The frontend supports cancellable searches, cached vessel details, keyboard-accessible selection, and a structured research dossier.

The engineering choices

The system keeps its public contracts separate from upstream response models and preserves attribution and data caveats in the interface. It deliberately uses native fetch and local React state, with no database, map library, or authentication until a real product need justifies them.

Engineering evidence

  1. Application-owned API contracts stay separate from upstream Global Fishing Watch response models.
  2. The access token and all Global Fishing Watch communication remain on the ASP.NET Core backend.
  3. Caching, request cancellation, concurrency coordination, and rate limiting protect upstream access and user interactions.
  4. Problem Details and xUnit coverage exercise validation, mapping, upstream failures, caching, and irregular registry data.

  2. 02 ASP.NET Core API
  3. 03 Global Fishing Watch

03 | Approach

Understand the system. Make the tradeoff. Leave it better.

I like to understand a system before changing it, but production work rarely waits for perfect context. My job is to find the important information, make a clear decision, and ship something that fits the system around it.

01

Orient first

Learn the shape of the product, its constraints, and the people who depend on it before choosing a solution.

02

Prefer the smallest useful change

Solve the actual problem without building a platform for hypothetical future requirements.

03

Design for the unhappy path

Loading, failure, stale data, conflicting records, and maintenance are part of the product, not cleanup for later.

04

Communicate the tradeoff

Make decisions understandable to technical and non-technical collaborators so the work can be trusted and maintained.
